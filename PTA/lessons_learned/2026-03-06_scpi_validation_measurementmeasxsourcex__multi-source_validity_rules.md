# Lessons Learned: SCPI Validation: MEASUrement:MEAS<x>:SOUrce<x> — Multi-Source Validity Rules

**Date:** 2026-03-06 16:19  
**Test Name:** SCPI Validation: MEASUrement:MEAS<x>:SOUrce<x> — Multi-Source Validity Rules

## Summary
Documents the conditional validity of MEASUrement:MEAS<x>:SOUrce<x> commands. SOU1 through SOU8 all validate against the programmer manual database as matching the canonical form MEASUrement:MEAS<x>:SOUrce<x>, but only SOU1 is unconditionally valid. SOU2–SOU8 are only valid at runtime when the active measurement type actually requires that many sources. This distinction matters for PI Translator XML generation and for .set file replay validation.

## Instruments Used
MSO 5/6 Series (any, applies to all MEASUrement commands)

## Key SCPI Commands
MEASUrement:MEAS&lt;x&gt;:SOUrce1  — always valid, every measurement type has at least one source
MEASUrement:MEAS&lt;x&gt;:SOUrce2  — valid only for 2-source measurements (e.g., DELay, SKEW, PHASE)
MEASUrement:MEAS&lt;x&gt;:SOUrce3  — valid only if measurement type takes 3+ sources (rare/none in practice)
MEASUrement:MEAS&lt;x&gt;:SOUrce4 through SOUrce8 — no known standard measurement type uses these; treat as NOP
MEASUrement:MEAS&lt;x&gt;:TYPe  — use this to determine number of required sources for a given measurement

## Gotchas / Problems Encountered
1. tek_validate_scpi reports MEASU:MEAS1:SOU2 through SOU8 as VERIFIED because they structurally match MEASUrement:MEAS&lt;x&gt;:SOUrce&lt;x&gt; in the programmer manual. The validator cannot detect runtime context — it only checks syntax, not whether the measurement type currently active actually requires that source slot.

2. Sending SOU2–SOU8 to a single-source measurement (e.g., FREQUENCY, RISETIME, AMPLITUDE) will generate an instrument error (Execution Error or undefined header). This silently corrupts the instrument error queue and may stall automation scripts that check *ESR?.

3. In *LRN? output and .set files, SOU3–SOU8 appear as NONE (unused source slots are preserved in state capture). Replaying these as-is to an instrument that only has a 1- or 2-source measurement active will cause errors.

4. There is no known standard MSO 5/6 measurement type that requires more than 2 sources. SOU3–SOU8 appear in *LRN? output purely as saved state placeholders.

## Solutions
1. For PI Translator XML: map MEASU:MEAS&lt;x&gt;:SOU2 through SOU8 to :HEADer OFF (NOP). SOU1 is NOT mapped — it passes through as valid.

2. For set_file_clean.py or similar .set file preprocessors: flag or strip MEASU:MEAS&lt;x&gt;:SOUn where n &gt; 1. If the MEAS&lt;x&gt;:TYP is known to be a 2-source type (DELay, SKEW, PHASE, etc.), SOU2 can be kept; otherwise strip it.

3. For tek_validate_scpi: remember that a VERIFIED result means syntactically valid, not contextually valid. MEASUrement:MEAS&lt;x&gt;:SOUrce&lt;x&gt; is one such case where runtime context is required to determine true validity.

4. Known 2-source measurement types: DELay, SKEW, PHASE. All others should be treated as single-source for the purpose of source slot validation.

## Measurement Tips
If building a .set file replay tool, read MEASU:MEAS&lt;x&gt;:TYP before sending any SOU&lt;n&gt; commands. Send SOU1 always. Send SOU2 only if TYP is DELay, SKEW, or PHASE. Discard SOU3–SOU8 unconditionally.

## Additional Notes
This lesson was discovered during PI Translator XML generation for UWIU_Ignit_ch1.set (MSO58LP source instrument). The tek_validate_scpi tool correctly identified the commands as syntactically matching the database but has no mechanism to enforce source-count constraints. This is a known limitation of static SCPI validation — the programmer manual defines the command form but not the runtime preconditions for multi-source argument slots.
